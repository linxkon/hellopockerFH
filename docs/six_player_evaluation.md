# 六人桌迭代评估方案

本项目以六人牌局作为策略迭代的标准评估环境。每桌放入 1 个待评估版本，以及由 2～3 个历史强版本组成的 5 个独立玩家实例。具体版本名单和实验结果记录在 [迭代目录](iterations/README.md)，本文规定比较方法，不预设某个策略长期最强。

已实现的批次入口为 `scripts/evaluate_iteration.py`，统计依赖见 `requirements-evaluation.txt`。配置指定 B/C/H 路径、配比、规则、各阶段配对数和种子；先冻结，再从快照中的脚本运行各阶段。现有冻结器支持单文件历史策略与本仓库的 Sohu 包装层、iter01 独立依赖；换成新的依赖结构时须补全冻结器，不能只复制入口。

```bash
.venv/bin/python scripts/evaluate_iteration.py \
  --config configs/iteration01.evaluation.json \
  --output "$HOME/.local/share/fullhouse-iterations/review-001" --stage freeze
.venv/bin/python "$HOME/.local/share/fullhouse-iterations/review-001/harness/scripts/evaluate_iteration.py" \
  --output "$HOME/.local/share/fullhouse-iterations/review-001" --stage control
```

其他阶段为 `screen`、`smoke`、`development`、`confirmation`；同一阶段目录已存在时拒绝覆盖。每阶段保存运行前计划、逐对原始结果、状态和 95% 分层配对 bootstrap 汇总。该入口复用 `backtest.run_match_inproc` 的比赛流程和已有 `ArenaEngine`，所有策略共用街道/金额观察与 HTTP 合法动作转换；原回测默认裁判保持原样。原建议非法、转换后提交合法、对外异常和超时分别报告。统计门槛只是评估的一部分，不能代替正确性及行为归因。

`scripts/replay_iteration.py` 对只读导出逐运行回放 B/B/C；`scripts/audit_iteration_traces.py` 对冒烟输入逐场回放。两者保持独立统计历史，结果保存在仓库外，不使用原牌谱结局给候选计算收益。`scripts/validate_iteration_arena.py --evaluation <冻结目录> --output <新的外部目录>` 运行三配比、两座位、C/B 共 12 场六客户端 HTTP 检查；其随机 Competition ID 会影响策略的 spot RNG，所以只作为接入验证。

## 1. 版本角色与选择

- **C（候选）**：本轮最新策略。
- **B（基线）**：本轮开始时冻结的已采纳版本，用来判断 C 是否带来提升。
- **H1 / H2 / H3（历史对手）**：从旧版本中选择的 2～3 个强版本，可以包含 B。按当前目标规则下的可比结果选择，记录收益、波动、样本量、稳定性和证据位置。

旧 README 的排名只能作为候选名单线索。缺少当前规则下的可比成绩时，先进行历史版本筛选评估，名单标为暂定；不能宣称已经选出了当前最优版本。筛选使用的样本与本轮最终确认样本分开。

没有显著可分辨的排名时，保留多个竞争版本，并说明不确定性。避免把只改名字或加载同一实际实现的文件当作不同历史版本。若只能确认两个强版本，使用双版本方案，不为凑数虚构第三个。

冻结完整依赖：入口文件、被加载策略、相关配置及源码哈希。尤其当前搜狐包装层会加载另一个基线文件，复制包装层本身不能冻结底层策略。评估过程中不要原地改写对手或基线；出现修正时重新标记版本和受影响的实验。

## 2. 六人桌组成

每桌始终只有 1 个 C，其余 5 个座位按下表填充；对照场把 C 替换为 B。

| 历史版本数 | 场景 | 被测版本 | H1 实例 | H2 实例 | H3 实例 |
|---|---|---|---|---|---|
| 3 | P1 | C 或 B × 1 | 2 | 2 | 1 |
| 3 | P2 | C 或 B × 1 | 2 | 1 | 2 |
| 3 | P3 | C 或 B × 1 | 1 | 2 | 2 |
| 2 | P1 | C 或 B × 1 | 3 | 2 | — |
| 2 | P2 | C 或 B × 1 | 2 | 3 | — |

同一轮所有场景等量评估、默认等权汇总，同时报告分场景结果。这样每个历史版本在全部场景中的出现次数一致，不会因长期占据更多席位主导评价。

“复制”指独立玩家实例，不需要复制多份相同源码：

- `backtest.py` 接受重复策略路径，生成不同玩家 ID，并分别加载顶层模块。当前 `bot_sohu_v16` 包装层及底层 `PLAYER_STATS` 也已检查为实例独立。
- 其他策略若通过普通 import 共享可变模块、外部文件或全局随机状态，仍需检查隔离与可复现性；顶层模块独立不代表任意依赖都自动隔离。
- local_arena 为 6 个座位创建不同凭证、状态目录和客户端进程；同一历史版本的多个客户端可以引用相同冻结文件。
- 每位玩家独立决策，不能共享私牌或对手画像；同版本重复席位不意味着协作。

按目标规则设置盲注、买入、补码、资金、每场手数及决策预算。`max_players=6` 只是上限，必须实际传入 6 个玩家。因资金不足等原因变成不足 6 人的后续牌局应单独标记、报告比例，不能悄悄算作满桌样本；不能为了维持满桌而改变目标规则且不披露。

## 3. 同桌对抗与基线比较

一组场景做两种配对运行：

1. C + 固定的 5 个历史实例。
2. B + 相同的 5 个历史实例。

C 已在直接与历史强策略对弈；第二组进一步回答“把原基线替换为 C，表现是否改善”。即使 C 尚未获得全桌最高收益，也可能明显优于 B；反过来，某次第一名也不能证明升级有效。

每一对使用相同规则、发牌种子、被测座位和对手席位顺序，各自从干净的实例状态开始；场内正常积累对手统计，跨场是否重置必须一致并记录。轮换被测玩家的 6 个座位，同时通过预先安排的对手顺序变化覆盖相对位置。对手顺序在同一配对中保持一致。

现有 `backtest.py ab` 会自动轮换被测玩家座位并逐场重新加载策略；对手的相对顺序需要在不同批次调整 `--field` 顺序。相同种子不是强行复用原牌谱：动作、参与人数和后续路径可能不同，策略自身的随机性也需要单独核实。

## 4. 分阶段执行

1. **正确性与接入检查**：跑相关回归，再对每个配比做小规模六人对弈，确认真实加载版本、独立实例、行动合法、计分正确、没有异常或预算问题。小样本只确认可运行。
2. **开发比较**：使用固定开发种子，在所有配比、座位安排下进行 C/B 比较。可先用每配比 120 对比赛估计耗时和波动，再根据预算规划样本；此数仅为起步示例，不是有效性的门槛。
3. **独立确认**：冻结候选后使用未参与筛选、调参的留出种子；运行前确定样本数、主要指标和采纳条件。不要反复看到领先就提前停止；留出结果若用于继续修改策略，下一轮需新的确认样本。
4. **HTTP 验证**：拟采纳的候选在 local_arena 中完成六客户端对弈，验证耗时、协议、恢复与日志。其吞吐和隔离机制与进程内回测不同，单独报告。
5. **结论与承接**：记录采纳、继续验证或放弃的证据。通过评估后按任务授权应用；是否更新历史对手池另行记录，新旧池结果不能不加区分地串成同一趋势。

每场手数应对应目标赛制；20 手、30 手或更长测试分开报告。扩大样本通常通过增加独立场次和种子，不悄悄把短局改成长局。若本轮只修改记录或工具，策略收益测试可注明不适用。

## 5. 评价什么

| 类别 | 应报告的信息 |
|---|---|
| 主要效果 | C、B 各自净筹码及按实际参与手数计算的 BB/100；配对的每场净筹码差 C−B 及其区间 |
| 分组稳定性 | 各配比、座位与独立种子批次的表现，不能只展示收益最好的场景 |
| 分布与风险 | 每场收益分布、较差场次表现、补码/资金不足情况；排名或首名频率作为辅助 |
| 运行可靠性 | 策略异常、非法动作、超时或回退、决策耗时；说明不同工具的记录口径 |
| 样本质量 | 实际场数、参与及结算手数、满六人覆盖、缺失/中断比例、规则和版本 |

优先按独立比赛或种子批次估计不确定性，同一场内多手牌和重复版本席位不能当作额外独立实验。现有 `ab` 输出的配对区间单位是筹码；搜狐模式的 `A_minus_B.bb_per_100` 为 null，应分别读取 A、B 的实际 BB/100。BB/100 差及其区间如需另算，应明确按实际手数处理，不能将配对筹码区间直接当成 BB/100 区间。

一轮开始前写清最小有意义改善、允许的分组退化和运行代价；没有足够证据时保留“继续验证”，不强行判断成功。结论限定为对这组历史强策略的表现，对真实线上对手的泛化还需独立证据。

## 6. 现有命令如何使用

以下是三历史版本的 P1 场景示例。路径需替换为本轮实际冻结版本；不表示这些占位版本已存在或已选出。

```bash
candidate_path='hero_bots/<候选版本>/bot.py'
baseline_path='hero_bots/<冻结基线>/bot.py'
history_one_path='hero_bots/<历史版本1>/bot.py'
history_two_path='hero_bots/<历史版本2>/bot.py'
history_three_path='hero_bots/<历史版本3>/bot.py'

.venv/bin/python backtest.py ab \
  --a "$candidate_path" --b "$baseline_path" \
  --field "$history_one_path" "$history_one_path" \
          "$history_two_path" "$history_two_path" "$history_three_path" \
  --competition-config configs/sohu.training.backtest.json \
  --hands 20 --matches 120 --seed-base 1000 \
  --budget 1 --no-ev --json
```

`--field` 必须恰好 5 项；A、B 分别进入六人桌，不是同时加入形成七人桌。`--no-ev` 使用实际收益，输出中的 EV 栏会镜像实际收益，不能称为独立的 EV 验证。把 JSON 标准输出保存到本轮独立结果文件，同时保存标准错误中的加载信息，避免覆盖旧报告。

P2、P3 调整重复次数；两个历史版本时使用 3+2 和 2+3。每个配比再按预定顺序排列对手，保持候选与基线的对应关系。单独观察候选同桌对抗也可用 `backtest.py eval` 传入候选加上述 5 个路径，并加 `--rotate-seats`。

HTTP 对弈使用 [local_arena 说明](local_arena.md) 创建 `--players 6` 的比赛，6 个客户端分别指定候选和历史策略路径；每轮使用新的比赛目录。

目前基础工具支持上述对弈与配对比较；历史版本筛选、多配比批次编排、统一报告及满桌覆盖统计仍需在具体迭代中执行和汇总，尚未集成为一条自动命令。本次方案没有选定历史冠军、运行收益实验或改动线上策略。
