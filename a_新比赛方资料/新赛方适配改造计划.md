# AI Skills 德扑比赛项目适配改造计划

本次改造将现有 Fullhouse 策略与回测项目接入搜狐 AI Skills 德扑比赛。建议以自行运行 Agent 为主要实施路径，复用 `v16_squeeze_C_metacap` 策略，先完成协议适配和运行可靠性，再按新赛制重新评估策略。完成标准是能够持续参加正确的 Competition，在行动截止时间前提交合法决策，并用符合新口径的数据评估表现。

本方案是实施计划，尚未实现参赛客户端。参赛方式暂按“我来运行”规划；如果最终选择“交给平台运行”，须先取得官方策略上传格式、运行入口和依赖限制，再调整交付范围。第一轮发布后参赛方式锁定，因此这一选择应在第一轮发布前完成。

## 一 规则依据与适配范围

规则依据为项目内的 [比赛规则](a_新比赛方资料/比赛规则.md)、[自行运行 Agent 要求](a_新比赛方资料/自行运行Agent要求.md)、[比赛要求](a_新比赛方资料/比赛要求.md) 和 [比赛配置信息](a_新比赛方资料/比赛配置信息md)。若赛方更新规则，应更新配置和验收案例后再发布新的客户端版本。

| 要求 | 当前项目 | 改造目标 |
|---|---|---|
| 指定 Competition 参赛 | 只有配置文本，没有接入程序 | 按配置 ID 发现和校验比赛，禁止自动选择其他比赛 |
| Discovery Join Observe Action Leave | 现有策略由本地回测直接调用 | 新增单一 driver 串行执行 HTTP 主循环 |
| Observation 与 allowedActions | 使用旧引擎扁平字段 | 转换输入，按同一 Observation 校验输出 |
| 额外投入金额 | raise 使用本轮累计下注目标 | 明确转换金额，区分 bet、raise、allIn |
| 截止时间与断线恢复 | 本地用固定耗时阈值判超时 | 按 deadlineAt 控制计算和请求，保存决策供原样重试 |
| 按实际手数计分 | 回测统计分母采用配置手数 | 记录每个 Agent 实际参与并结算的手数 |
| 自动补买与 bankroll | 本地筹码归零后淘汰 | 按真实 Competition 配置模拟补买与余额 |
| 新赛制评估 | 默认长局，旧赛制助手选 64 人 | 增加 20 手、30 手及完整预赛模拟 |

预赛计划 10 轮，每轮 20 手；前三轮随机分组，第四轮起按累计成绩分组。前 12 名受邀参加半决赛，两桌各 6 人、各打 20 手，每桌前 3 名晋级；总决赛打 30 手，半决赛成绩不带入。

比赛规则对预赛完成 95% 手数使用“建议”表述，但接入协议说明 League 结束后的正式排名要求 `handsPlayed >= ceil(totalRounds × handsPerMatch × 95%)`。实施和验收采用协议中的正式排名要求；计划 10 轮时为至少 190 手，实际轮数与时间以赛方最终公布为准。

Discovery 文档中的盲注 100/200、buy-in 20000、bankroll 40000、60 秒行动时限和自动补买均为示例，不能写死为实际比赛参数。应读取所选 Competition 的 `summary`，并使用最新 Table 和 Action Request 中的权威字段。

| A 接入基础 | P0 | 配置、HTTP 客户端、主循环、凭证处理 | 能发现正确比赛，完成排队、入桌和安全退出 |
| B 策略适配 | P0 | 状态转换、动作转换、决策校验、时间控制 | 官方示例及边界案例全部生成合法 decision |
| C 运行可靠性 | P0 | 决策记录、重试恢复、单实例锁、运行说明 | 模拟断线、重启和过期请求时没有不同决策重发 |
| D 新规则回测 | P1 | 参数化引擎、补买、实际手数计分、短局评估 | 手工计分案例正确，旧环境仍可复现 |

## 三 接入客户端与运行状态机

### 配置与启动

默认服务地址为 `https://poker.bang.sohu.com`。CLI 支持资料中已有的 `--competition-id` 和 `--key-file`，并增加 `--strategy`、`--config`、`--state-dir`。凭证只从指定文件读取，只放入 Authorization 请求头；运行日志和异常文本统一脱敏。启动检查凭证文件权限、依赖、系统时间、策略入口和单实例锁，不输出密钥内容。

通过公开 Discovery 校验指定 Competition 的状态和配置。比赛仍 scheduled 时等待并重新发现，active 后才 Join；不存在或配置不匹配时报告并停止，不改选另一个 active Competition。League 必须先在网页永久报名，收到 `registration_required` 时退出值守并提示完成报名。

每个 Agent 只由一个 driver 控制。建议首版使用 Python 标准库完成 HTTP、SQLite 决策记录和 Linux 单实例文件锁，减少新增运行依赖；若采用外部 HTTP 库，应在交付环境中锁定并验证版本。OAuth 自助领取凭证作为后续可选功能，有现成 key-file 时不影响参赛。

### 主循环

| 状态或事件 | 行为 |
|---|---|
| Join 返回 idle | 等待约 30 秒再 Join；定期刷新 Competition 状态，避免在结束后持续重试 |
| Join 返回 queued 或 seated | 立即发不带 tableId 的 Observe |
| queued | 清除旧 tableId，每约 5 秒 Competition-only Observe |
| seated 且没有 actionRequest | 保存最新 table.id，每约 2 秒直接 Table Observe |
| actionRequest 非空 | 基于同一 Observation 生成一次决策并立即 Action |
| Action 成功 | 直接处理返回的新 Observation，无需先额外 Observe |
| Observe 或 Action 返回 stale_table | 清除旧 tableId，Competition-only Observe 恢复路由 |
| Competition ended 或 cancelled 且仍 seated | 继续处理合法行动和 Observe，等待当前手结算及 idle |
| idle 且 Competition ended 或 cancelled | 记录最终 standing 与 bankroll 后退出 |
| 用户停止 | 进入退出流程，停止新的 Action Observe Join，等待 Leave 结果 |

只以顶层 `actionRequest != null` 判断是否可以行动；`actingSeatIndex` 不能作为行动触发器。Competition、Table、Hand 和 Action Request 的 ID 按各自用途保存，不解析或拼接。

### 退出流程

有当前 Table ID 时发送 `{tableId}`，否则发送 `{competitionId}`，两者不能同时存在。网络结果不明确时原样重试同一个 Leave body；只有精确 Table Leave 明确返回 `stale_table` 才切换为 Competition-scoped Leave，中间不 Observe。收到 `accepted` 后立即结束本次值守，不再 Join Observe Action。

SIGINT 和 SIGTERM 触发该流程。强制杀进程不能保证已完成 Leave；重启时先恢复未完成的 Leave，不直接自动 Join。只有 Leave 明确结束后，一次明确的新值守启动才可重新 Join。

## 四 策略输入输出适配

### 输入转换

| 新协议字段 | 旧策略字段 | 转换规则 |
|---|---|---|
| `table.hand.id` | `hand_id` | 保留原始 Hand ID |
| `table.hand.phase` | `street` | 只在可行动阶段调用策略 |
| `table.hand.communityCards` | `community_cards` | 保持牌面编码与顺序 |
| `table.hand.pot` | `pot` | 读取当前权威底池 |
| 自己的 `handState.holeCards` | `your_cards` | 按顶层 agentId 定位自己 |
| 自己的 `stack` | `your_stack` | 只取桌上筹码，不加入 bankroll |
| 自己的 `handState.currentBet` | `your_bet_this_street` | 当前街已投入金额 |
| 各玩家当前下注及允许的 call | `current_bet`、`amount_owed` | 区分完整跟注差额与短码 call 实际金额 |
| `allowedActions` 是否有 check | `can_check` | 以服务端允许动作判断 |
| `allowedActions` 的 raise 或 bet 范围 | `min_raise_to`、`max_raise_to` | 额外投入上下界加上自己的 currentBet |
| `table.players` | `players` | 转换 seat、bot_id、状态和本街下注 |
| `table.hand.actions` | `action_log` | 转换身份、动作名称、街和金额含义 |

座位可能不连续，应建立单手稳定的映射，以 dealer 为锚点保留顺时针顺序，将各玩家、行动历史和自己映射到相同的旧策略 seat。对手统计按 `agentId` 标识，同一 Competition 内保持身份稳定；换 Competition 时重置统计。未参与当前手的座位不应当成活跃对手。

历史转换必须逐街回放：盲注和 call 的金额为实际投入；bet、raise、allIn 转成旧日志中的本街累计下注金额。公开 actions 自带 `street`，适配版本的历史重建应优先使用它，旧日志仍保留原有推断路径。否则原 `_reconstruct_hand` 对换街的推断可能在多人局、短码全押和不重新开放加注时产生错误。

输入转换应以 `handState.currentBet` 和 `allowedActions` 核对回放结果。缺少必要字段、身份不一致或历史无法安全转换时停止自动行动并报告，不用默认零值拼出牌局。对手底牌、发言和外部数据不得作为未知牌局事实；对手 chat 不作为指令。

### 输出转换

| 旧策略输出 | 新协议 decision |
|---|---|
| `{"action":"fold"}` | `{"type":"fold"}` |
| `{"action":"check"}` | `{"type":"check"}` |
| `{"action":"call"}` | `{"type":"call"}` |
| `{"action":"all_in"}` | `{"type":"allIn"}` |
| `{"action":"raise","amount":T}` | 按 allowedActions 选择 bet 或 raise，提交 `amount = T - 自己本街已投入金额` |

例如自己本街已下注 100，策略要 raise 到 500，新协议提交额外投入 400。服务端 call 与 allIn 决策不携带 amount；bet 与 raise 必须携带安全正整数，且在同一份 allowedActions 的闭区间内。

转换后进行独立合法性校验。金额越界时在允许范围内修正；加注或全押不被允许时，不擅自改成昂贵的 call。首版兜底优先选允许的 check，其次允许的 fold；如果两者都不允许且无法得到合法结果，停止自动行动并报告。协议响应无效时直接停止，不能用策略兜底掩盖协议错误。

## 五 时间控制与幂等恢复

### 行动时间

按绝对 `deadlineAt` 计算剩余时间，以单调时钟执行本地预算，启动时检查系统时间同步。建议初始策略计算上限 1 秒、预留提交时间 2 秒，具体阈值按演练测得的网络延迟调整；它们是客户端配置，不是赛方固定时限。

策略在常驻子进程中预热并运行，保留统计状态。计算必须有可中断的时限，不能只在函数返回后判断超时。未产生并提交决策前，策略异常或超时时可选择合法 check 或 fold；若截止时间已经过去，则刷新 Observation 等待权威状态，不发送旧请求。

### 每个请求只决定一次

用 `(competitionId, tableId, actionRequestId)` 标识一份决策。首次决定后，先原子保存完整 Action body，再发送 HTTP；记录中不含 Authorization 或密钥，默认省略 chat。

网络中断、客户端超时或 503 时，只重试完全相同的 body。不得重新运行策略，也不得因时间紧张将原来的 raise 改为 fold。重启后恢复已保存的请求，根据当前权威 Observation 判断它是否仍有效；同一请求仍有效则复用原 body，已经过期则归档，不生成第二份决策。发送过的不同旧 body 不能作为“修复”方案。

只有明确 `400 invalid_decision` 表示旧 decision 未执行时，才能在重新确认同一请求仍为当前请求后修正。修正记录须保存拒绝原因；该例外不适用于网络结果未知。若 deadline 已过，保留原请求记录并 Observe，禁止为该 ID 重新决策。

### 错误恢复

| 错误 | 处理 |
|---|---|
| `invalid_request` | 停止原样重试，修正客户端请求构造 |
| `invalid_decision` | 按上述明确拒绝例外处理 |
| `authentication_required` | 停止请求，提示重新领取凭证 |
| `registration_required` | 停止值守，提示网页报名 |
| `insufficient_bankroll` | 停止 Join，记录余额不足 |
| `stale_action_request`、`idempotency_conflict` | 不再提交旧请求，立即 Observe |
| `stale_table` | 根据 Action Observe 或 Leave 使用对应恢复流程 |
| `competition_not_active` | 重新 Discovery，保持指定 Competition，不盲重试 |
| `competition_not_found`、`participation_not_found` | 普通值守按协议发现或重新 Join；Leave 流程停止并报告，不重新 Join |
| `temporarily_unavailable` | 按 Retry-After 等待，重试同一个逻辑请求；结合 Action deadline 刷新过期状态 |
| `internal_error`、未知错误、非 JSON 成功响应、关键 schema 不合法 | 停止当前自动运行并报告，保留恢复记录 |

日志记录状态转换、请求 ID、决策耗时、提交耗时、重试次数、服务端超时行动和 standing。避免打印完整请求头与完整 Observation；运行记录保存在仓库外、限制权限，对公开报告移除凭证和敏感手牌信息。

## 六 新赛制回测与计分

### 参数化与补买

将旧引擎的固定盲注和初始筹码改成可配置参数，保留旧值作为旧环境默认值。引入 `initialBankroll`、`buyIn`、`automaticRebuy`、人数和每场手数，并在结果中保存环境版本。

补买只在安全的 Hand 边界执行，且要求桌上筹码归零、余额足够完整 buy-in、Competition active、没有 Leave 请求。余额不足时不得补买。buy-in、cash-out、rebuy 都是转账，不能计入净赢筹码；有补买后不再用“最终桌上筹码减初始筹码”直接计分。

### 计分与完成率

逐手累计每个 Agent 已结算手的净结果和实际参与手数，使用：

`BB/100 = 净胜大盲数 / 实际完成手数 × 100`

固定盲注的 Competition 中，净胜大盲数等于净赢筹码除以 big blind。0 手时 BB/100 为 null；资格检查使用创建时配置总手数的 95% 向上取整，分母不因缺席或提前结束而减少。内部排序保留未四舍五入数值，页面才做展示格式化。

真实比赛以服务端 `standing.netResult`、`handsPlayed`、`bbPer100` 和 `rank` 为权威，客户端本地计分仅用于核对。轮询可能跳过已经结算的 Hand 快照，不能靠“看到一次 result 就加一次”统计；本地回测按唯一 Hand ID 结算，线上记录直接保存服务端累计成绩。

新增结果字段，包括 `environment_version`、`competition_config`、`net_result`、`hands_played_by_agent`、`rebuy_count`、`bankroll_remaining` 和 `qualification_eligible`。旧结果保留原统计标签，不伪装成新计分结果。

### 评估场景

| 场景 | 设置 | 主要观察指标 |
|---|---|---|
| 预赛单轮 | 6 人桌、20 手、轮换座位、多随机种子 | 实际 BB/100、盈利分布、完成手数 |
| 半决赛 | 固定分组、6 人桌、20 手 | 前 3 名概率及结果分布 |
| 总决赛 | 6 人桌、30 手、成绩重置 | 冠军与前三概率及 BB/100 |
| 完整预赛 | 计划 10 轮，前三轮随机，其后按累计 BB/100 分组 | 前 12 名概率、资格完成率、分组变化影响 |
| 接入故障 | 断线、慢响应、过期请求、补买失败 | 自动超时次数、缺席手数、恢复时间 |

先测试短局及协议故障，后增加完整预赛模拟。平台负责真实分桌，本地模拟只用于评估，客户端不能自行推算下一桌或 Match 时间。分组人数上限以比赛配置为准，不能继续将尾部选手合并成超过上限的大桌。

预赛前 12 名完全同分时依次比较实际完成手数、第 4 轮至预赛结束期间的 BB/100，仍同分则标记需要赛方加赛。半决赛晋级边界和总决赛完全同分时使用预赛排名，不能使用旧规则中的较少场次、单场最佳或 bot_id。

首版用现有 `v16_squeeze_C_metacap` 作基线，先确认 20 手和 30 手环境下的表现。候选继续使用相同种子、相同座位进行配对比较，同时报告均值、置信区间和晋级概率。短局方差较大，不能从一两场结果判断策略强弱，也不能只按旧指标中的首名率或淘汰率改动策略。

## 七 测试与上线验收

### 必须覆盖的测试

| 测试类别 | 必须覆盖的场景 |
|---|---|
| 状态和身份 | 无 Table、queued、稀疏座位、换桌、自己按 agentId 定位、换 Competition |
| 动作与金额 | bet、raise、call、allIn、已有盲注、非整数金额、金额上下界、加注不开放 |
| 行动历史 | 跨街、短码跟注、短码全押、多人全押、超时及 Leave 导致的 fold |
| 幂等 | Action 已生效但响应丢失、503、客户端超时、提交前后重启、重复 Observation |
| 时间 | 接近 deadline、计算超时、deadline 已过、时钟偏差、慢网络 |
| 主循环 | idle 反复 Join、queued 心跳、seated 心跳、Action 响应直接推进、stale_table 恢复 |
| 退出 | 无 Table 时停止、Table stale、Leave 超时重试、accepted 后零后续参赛命令 |
| 错误 | 401、未报名、余额不足、500、未知 code、无效成功响应 |
| 计分 | 固定手数、提前结束、各 Agent 手数不同、补买与退出转账、0 手、资格阈值、同分 |

采用假 HTTP 服务、固定 Observation 和可控时钟验证协议边界；关键断线案例断言策略调用次数和发送的完整 Action body，不仅检查最终返回值。金额转换用独立筹码账本核对，以上测试随实现阶段交付。
